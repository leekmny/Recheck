# 캡스톤 피드백: 요구사항, 검증 근거와 발표 구성

2026-11-18 재점검 기록입니다. 주된 사용 시나리오는 **레거시 프로그램을 새 구현으로 교체하기 전에 관찰 가능한 동작 차이를 확인하는 것**입니다. 실제 산업 도입 사례나 고객과 합의한 요구사항을 확보했다는 뜻은 아닙니다. 예시는 직접 작성한 평가용 프로그램을 사용합니다.

포팅 시나리오 확장의 실험은 같은 논리 입력의 실행 일치, 원본과 새 구현 각각의 요구사항, 구조 근거를 따로 평가합니다. [업데이트와 실제 실험 근거](PORTING_VALIDATION_UPDATE.md)

## 목적과 구성요소의 역할

소스가 없거나 유지보수하기 어려운 기존 프로그램을 새로 구현할 때, 사용자는 필요한 동작이 보존됐는지 확인해야 합니다. Recheck는 사용자가 준비한 두 프로그램과 입력을 받아 차이·관측 범위·재현 근거를 정리합니다. 원본의 동작을 정답으로 삼을지는 사용자의 요구사항에 달려 있습니다. 원본에도 결함이 있을 수 있고, 의도적인 변경은 차이가 발견되더라도 요구사항을 충족할 수 있습니다.

| 구성요소 | 맡는 역할 | 확인하지 않는 것 |
| --- | --- | --- |
| 원본 (`original`) | 사용자가 준비한 기준 실행 파일 | 모든 동작이 요구사항의 정답인지 여부 |
| 재구현 (`reimplementation`) | 사용자가 별도로 만든 대체 후보 | 원본에서 자동 복제한 결과라는 주장 |
| Ghidra·REA | 함수·추정 의사코드·CFG·호출·명령 또는 .NET 메타데이터 수집 | 원본 소스 완전 복원, 실행 동등성 증명 |
| Docker 실행 어댑터 | 같은 환경·입력·자원 제한으로 실행하고 원시 stdout·stderr·종료 코드 기록 | Windows·GUI·네트워크 등 미지원 실행, 임의 코드에 대한 완전한 보안 |
| Recheck | 입력·환경·해시·수집 범위 관리, 정적 후보·실행 쌍 비교, 화면·보고서 | 외부 도구 자체를 개발했다는 주장, 자동 복제·복호화·권리 판정 |
| 선택한 AI | 근거를 인용한 차이·관련 함수 설명과 추가 확인 제안 | 실측 수치 대체, 원인 확정, 저작권 침해 확률 산출 |

흐름은 `사용자 원본 + 사용자 재구현 + 같은 입력 → 정적 근거 / 격리 실행 관찰 → Recheck 비교·보고서 → 사용자의 요구사항 판단`입니다. AI는 선택 사항입니다. 현재 동적 실행은 Linux x86-64 ELF 콘솔 프로그램용입니다. 정적 파일 허용과 실행 지원은 별개이며 [분석 모드](ANALYSIS_MODES.md)와 [지원 매트릭스](DISTRIBUTION_AND_RECOVERY.md#파일-지원-매트릭스)를 따릅니다.

GUI의 **기존 프로그램 다시 만들기·프로그램 개선하기 · 준비 중**과 CLI의 `reconstruct`·`modernize`는 요청·원본 보관 단계입니다. [재구현 서비스](../recheck/reconstruction.py)는 `generation_pipeline_not_implemented`로 차단하고 `NOT IMPLEMENTED`를 기록합니다. 이를 자동 생성·빌드·복제 성공으로 설명하지 않습니다.

## 요구사항 추적표

‘이미 충족’은 이번 피드백 이전에도 코드·문서에 있던 동작입니다. ‘일부 충족’은 설명·예외 처리·실측 범위의 보완이 필요한 상태입니다. ‘미충족’은 필요한 구현·자료의 부재가 확인된 상태이고, ‘확인 불가’는 판단할 자료나 실험이 부족한 상태입니다. 단위 검사, 실제 도구 실행, 새 배포본 검증을 구분합니다. 아래 상태는 보완 전 점검 시점 기준이며 기존에 충족하던 기능을 새 기능으로 계산하지 않습니다.

| 탐지 향상·완전 동등으로 과도한 일반화 | 기존 3쌍·각 1회·메모리 미측정·일반화 제한 | 일부 보완 필요 | 같은 표본의 동적 단독 기준과 비교 | 단위·분모·오류·불확실성 제시; 향상은 연구 질문으로 유지 |

## 지표를 읽는 방법

네이티브 함수 후보 점수는 비자동 함수명 일치, CFG 노드 수·간선 수의 비율, 해결된 호출 수의 비율, mnemonic 다중집합 Jaccard를 가중합한 휴리스틱입니다. CFG 연결 형태 전체, 호출 대상의 의미, 피연산자·상수 또는 모든 경로의 결과를 증명하는 값이 아닙니다. 가중치·후보 임계값·탐색 제한은 [실제 구현](../recheck/comparison.py)을 따릅니다.

이번 보완에서는 함수 목록 전체와 비교 가능한 함수, 미관측 함수, 외부 함수를 구분합니다. 관측된 구조가 없는 함수를 ‘같은 빈 구조’로 점수화하지 않습니다. 전체 점수는 비교 가능한 함수 범위의 값이며, 양쪽 중 한쪽이라도 비교 가능한 함수가 없으면 `null`·미측정입니다. 미관측·후보 탐색 생략이 있으면 부분 범위로 표시합니다. 이 분모 변경을 성능 향상 수치로 해석하지 않습니다. .NET은 별도의 시그니처 대응과 CIL 관측을 사용합니다.

동적 비교는 유효하게 관찰한 양쪽 실행의 stdout·stderr·종료 코드를 저장된 정책으로 대조합니다. 정규화가 켜졌다면 원시 바이트가 달라도 정책상 일치일 수 있습니다. timeout·취소·OOM·출력 잘림·관찰 손상·입력 재현 실패는 미측정이며 그 입력이 같다는 결론을 내리지 않습니다. timeout 한 번으로 무한 루프나 비종료를 확정하지 않습니다. 같은 비정상 종료도 유효 관찰이면 비교할 수 있으나 업무 요구의 성공을 뜻하지는 않습니다.

아래 표는 **지표 해석 예시이며 새 실험의 측정 수치가 아닙니다**.

| 정적 관찰 | 동적 관찰 | 허용되는 해석 | 다음 확인 |
| --- | --- | --- | --- |
| 분기·명령 수가 매우 비슷함 | 경계 입력의 출력이 다름 | 구조가 비슷해도 등록 입력에서 차이가 있음 | `<`·`<=`, 상수·반올림 등을 확인하고 경계 전후 입력 추가 |
| 분기식과 반복·배열 구현의 구조가 다름 | 등록한 배송 요금 입력은 모두 같음 | 해당 입력에서는 같지만 구현 구조가 다름 | 미등록 구간·범위 밖·오류 입력 확인 |
| 정적 근거 미관측 | 실행 관찰은 같음 | 구조는 미검증, 등록 입력에서만 같음 | 필요한 정적 근거 수집 또는 한계 기록 |
| 정적 후보가 연결됨 | 일부 입력 timeout | 관측 구조만 설명 가능, 해당 입력 미측정 | 자원 제한·종료 조건·환경을 확인한 새 실험 |

## 실제 실험과 근거의 상태

### 기존 고정 정답 평가의 현재 실행

기존 `samples/accuracy/oracle.json`의 6개 프로그램 계열·71입력·5유형을 새 실행 ID로 평가했습니다. 이는 355개의 독립 프로그램이 아니라 **355개의 입력 쌍 판정**입니다. 기본 Managed 경로는 33개 ELF 빌드 후 pin된 실행 이미지가 없어 대상 실행0회로 차단됐습니다. [차단 기록](../benchmarks/results/accuracy-20261118-managed-original/blocked-summary.json)을 보존했습니다.

제품의 기본 경로·manifest 검증은 유지하고, 기존 평가기에 **명시적 `--execution-image`를 지정했을 때만 standalone Docker 기준선**을 선택하는 옵션을 추가했습니다. 대표1입력의5판정(대상6회+복구3회) 확인 후, 동일한 기존 정답표 전체를 별도 실행했습니다. [전체 실측·재현 근거](../benchmarks/results/accuracy-20261118-standalone-full/README.md)는 **355/355측정·미측정0·기대19/관찰19불일치·오탐0·미탐0·oracle 오류0**, 대상426회+복구3회입니다. 기준 출력은 비교 유형 사이에서 재사용했고 동일 파일 비교의 오른쪽은 별도 실행했습니다. timeout·출력 제한·자식 프로세스 복구3건은 미측정으로 처리하고 컨테이너 제거를 확인했습니다. 저장 오류·관찰 snapshot 불일치도0건입니다.

이 결과는 **현재 소스와 실제 설치 이미지에서 기존 입력·정답을 다시 평가한 standalone 출력 비교 결과**입니다. 과거 감사 보고서의19/19를 복사하지 않았으며, 제품 Managed 실행이나 전체 Engine·정적 추출·AI 설명의 성공으로 쓰지 않습니다. 이 기존 평가는 AI 요청0회입니다. 빌드 산출물 재사용 시 실제33개 ELF의 SHA를 전부 확인했습니다. PE·정적 품질·AI 설명은 이 하네스의 평가 대상이 아닙니다.

### 기존 A/B/C와 신규 실험의 구분

기존 [벤치마크 안내](../benchmarks/README.md)는 직접 만든 3쌍을 대상으로 A(정적 근거를 받은 AI 예측), B(동일 실행 어댑터의 직접 비교), C(제품 엔진)를 구분합니다. 과거 20입력의 2차이·18정상, A의 오탐·판정불가와 C 해석 실패는 **과거 기록의 요약**입니다. 원시 결과 디렉터리가 없는 새 checkout에서 그 수치의 재계산·재현을 완료했다고 말할 수 없습니다. 과거 실패를 새 성공으로 바꾸지 않습니다.

기존 두 CLI의 `--help`와 실제 `--prepare-only`를 호출했습니다. 준비 단계는 기존 compiler wrapper의 `/out` 권한 오류로 먼저 실패했고, 별도의 원래 JSON reader 호출은 할인 샘플 `tests.json` 부재를 확인했습니다. 과거 원시 snapshot도 없습니다. [기존 실험 가용성·실패 원문](../benchmarks/results/legacy-abc-20261118-availability/README.md)에 자료 계약과 복구 조건을 기록했습니다. 원래 A/B/C는 이번에 완료하지 못했으며, 새 소스 기반 LLM 실험을 Ghidra 정보 기반 A로 대체하지 않았습니다.

현재 브랜치의 신규 반례 실험은 [capstone-20261118-v2](../benchmarks/results/capstone-20261118-v2/README.md)에 기록했습니다. 6유형·7쌍·24입력(정상 동작 비교 22개, timeout·미지원 2개)이며 기존 A/B/C의 정확한 재현과는 다릅니다. 기존 A의 Ghidra 함수 자료 대신 신규 LLM 조건에는 자체 작성 C 소스를 제공했습니다.

이번 실측이 확인한 것은 출력·종료 코드 비교, 불확실한 실패를 유보해야 하는 이유, 고정 자료에서 모델 오탐과 실패 처리 오류가 발생한다는 사실입니다. 함수 대응 정확도, AI 원인 설명 정확도, 구조 분석의 추가 탐지 효과, 팀원 재현 시간 감소는 미측정입니다. JSON 근거 연결 회귀 검사 통과와 올바른 원인 설명의 실증 평가는 구분합니다.

## 프롬프트 방향과 기준 커밋 검증

잠금 의존성을 설치한 Windows CPython3.14.10 전용 `.venv`에서 검사했습니다. 변경 전 전체 pytest는 2156통과·3skip·4setup error였습니다. 4건은 모두 `tests/test_distribution_notices.py`의 `cpython_ssl_files` fixture에서 uv Python 별칭 경로와 resolve한 실제 경로를 비교하는 문제입니다. 원래 기준선 기록은 로컬 `verification/baseline-tests.xml`과 `baseline-tests.txt`에 있습니다. 이 배포 검사 오류를 이번 검증 비교 코드의 성공으로 덮지 않습니다.

## 발표에 포함할 여섯 항목

### 1. 도입: 해결하려는 문제

“기존 프로그램을 새 구현으로 바꿀 때, 같은 입력에서 어디가 달라지는지와 아직 확인하지 못한 범위를 함께 확인하고 싶다”로 시작합니다. 대상은 원본·대체 후보를 이미 갖춘 사용자입니다. 자동 복제나 정적 분석만으로 전체 동등성을 확정하는 도구로 소개하지 않습니다. 산업 사례는 확보 전이므로 사용 시나리오로 제시합니다.

### 2. 작은 예시: 입력에서 결과까지

[직접 작성한 배송 요금 샘플](../benchmarks/samples/)에서 기존·새 프로그램을 고르고 경계 전후 입력을 넣는 흐름을 보여 줍니다. 두 프로그램의 제작 주체, 기대값을 정한 기준, 테스트가 확인하는 구간을 설명합니다. 원시 출력·종료 코드 → 불일치 입력 → 관련 정적 근거 → 선택한 AI 설명 순서로 읽습니다. 실행하지 않은 예시는 ‘설명용’으로 표시하고 실측 숫자를 붙이지 않습니다.

### 3. 지표 충돌: 구조 유사도와 동작 비교

위 표의 ‘비슷한 구조·다른 경계 출력’과 ‘다른 구조·같은 등록 출력’을 나란히 제시합니다. 두 지표를 단순 평균이나 최종 동등 확률로 합치지 않습니다. 정적 근거의 역할은 관련 함수 후보와 추가 검토 지점을 제시하는 것입니다. 실제 원인은 조건 검토와 추가 실행으로 확인합니다.

### 4. 실제 실험: 질문·기준·관찰의 구분

자체 샘플의 기대값을 먼저 고정하고 입력 쌍 단위로 동적 단독 기준과 제품 결과를 비교합니다. 정적 방법·AI를 평가할 때는 제공한 소스·추출 근거·입력의 범위를 명시하고 정답 없는 예측을 먼저 보존한 뒤 실행 정답과 대조합니다. 원 C 소스를 받은 모델과 Ghidra 근거만 받은 모델은 같은 조건이 아닙니다. 실행 결과를 고정해 제공한 모델의 설명을 자율 도구 사용 에이전트 실험으로 부르지 않습니다. 불일치 검출·오탐·누락·판정불가, 함수 후보 연결, 설명의 정확성을 각각 보고합니다. 미실측 메모리·단계는 미측정·미실행으로 표시합니다.

### 5. 한계: 실험이 답하지 못한 것

유한 입력은 전체 동등성을 증명하지 않습니다. 작은 자체 콘솔 샘플은 산업의 GUI·동시성·상태·네트워크·시스템 연동을 대표하지 않습니다. 동적 실행은 Linux x86-64 ELF 콘솔로 제한되며 Windows 실행 worker와 깨끗한 VM 검증은 별도 미완료 항목입니다. 컴파일러·최적화·심볼·수집 누락·정규화 정책이 결과에 영향을 줄 수 있고, 실제 확인한 조건만 보고합니다. 새 EXE를 빌드·검증하지 않았다면 소스 검사를 배포본 검증으로 설명하지 않습니다.
