# Recheck 완성도 개선과 비교 형식 확장안

작성일: 2026-11-16. 캡스톤 디자인 주제: **프로그램 동작 비교 및 AI 근거 분석 도구 Recheck**.

이 문서는 공개 0.1.0를 비교 기준으로 작성한 **계획**이다. 0.1.1에서는 Gemini 3.5 Flash-Lite의 실제 응답·JSON·도구 왕복·고정 비교 설명을 검증했고, 무료 키 발급 안내와 ZIP 구성 비교의 첫 단계를 구현했다. 아래 36개 제안 전체가 완료됐다는 뜻은 아니다. 기존 사용자의 AI 선택은 보존하며 자동으로 유료 모델로 전환하지 않는다.

## 먼저 집중할 세 가지

1. **Gemini 무료 시작 흐름을 실제 설명까지 검증한다.** 기본 시작은 Gemini 무료 등급, 별도 추천은 GPT로 표현한다. 키 저장·작은 응답·JSON/도구 기능·실제 고정 비교 설명·재시작 재사용을 확인한 뒤 새 사용자 기본값을 바꾼다. 무료 한도/모델 변경 또는 실패 시 유료 모델로 자동 전환하지 않는다.
2. **ZIP 구성 비교를 첫 새 형식으로 만든다.** 파일 목록·내용 해시·추가/삭제/변경을 보여주며 실행 일치율과 섞지 않는다. 이후 명시적으로 선택한 내장 EXE/DLL/ELF를 기존 분석에 연결한다. 패키지 안의 파일을 호스트에서 실행하지 않는다.
3. **WASM 구조와 ASAR/APK 메타데이터로 확대한다.** 공통 자료형과 근거 참조를 먼저 만들고 개별 도구를 연결한다. Windows PE 동작 비교는 중요하지만 별도 Windows worker와 실제 실행 환경이 필요하므로 독립 마일스톤으로 관리한다.

Gemini·GPT의 설명 품질 우열은 이 문서에서 실측한 사실이 아니다. 기본값과 추천을 구분하는 것은 사용자의 제품 정책이며, 고정 정답과 비용·지연·실패율 평가로 지속 확인할 대상이다.

| 영역 | 현재 확인되는 구현 | 추가로 필요한 부분 |
| --- | --- | --- |
| 입력·비교 | ELF/PE/단일 Mach-O 식별, 네이티브 함수·관리 메서드 구조 비교 | 패키지·스크립트·APK·WASM 등은 제품 비교 경로 미연결 |

| 정적 근거 | REA/Ghidra의 디컴파일·CFG·호출·명령, .NET 시그니처·CIL·예외 영역 | 형식별 엔터티와 관계, 각 도구의 누락/지원 범위, 함수 외 근거 연결 |

현재 정적 허용 범위가 실제 도구·아키텍처 전체의 실측 성공을 뜻하지 않는다. 실행 미지원 형식의 정적 비교를 프로그램 동작 동등성으로 표시하지 않는다.

## 우선순위와 난이도

P0는 현재 사용 흐름의 신뢰성과 기본값 검증, P1은 다음 기능 확장, P2는 공통 구조를 갖춘 뒤 추진할 기능, P3는 별도 환경·규모가 큰 장기 구상이다. 난이도 S는 기존 경로의 작은 확장, M은 여러 화면/계약·도구 연결, L은 실행 환경·보안/증거 계약을 포함하는 큰 작업이다. 이는 작업량의 상대 구분이며 일정 약속이 아니다.

## 형식 확대를 위한 공통 구조

현재 경로에는 함수 밖의 구조를 넣을 때 막히는 지점이 있다.

- `recheck/models.py::inspect_binary`는 ELF·PE·thin Mach-O와 `analysis_kind=native/managed`를 중심으로 판별한다. 새 형식의 실제 magic/내용 식별과 capability를 별도 등록해야 한다.
- `recheck/engine.py::analyze`는 정적 분석에서도 실행 입력을 `validate_tests()`로 검증한다. 패키지 구성 비교는 실행 테스트 0개가 정당하므로 전용 계약을 둬야 한다. 가짜 입력을 하나 넣어 우회하지 않는다.
- `Engine._pipeline`은 모든 분석에서 대상 OS 일치를 요구하고 구조 비교에 `functions`를 확인한다. OS가 없는 패키지는 실행 호환성 검사를 그대로 적용할 대상이 아니다.
- `recheck/adapters.py::StaticArtifact`는 함수·주소·CFG·호출·명령을 필수로 요구한다. ZIP 구성원·manifest·DEX·WASM import를 가짜 함수로 만들지 않는다.
- `recheck/comparison.py::compare_static_artifacts`는 native/managed만 처리한다. `artifact_kind`에 따른 comparator와 결과 스키마가 필요하다.
- `recheck/analysis_environment.py::StaticRouter`, `static_backend.py::_validate_artifact`, `resources/docker/static/worker.mjs`의 선택·검증·고정 도구 식별을 새 worker 계약에 연결해야 한다.
- `recheck/report.py`, GUI 결과 화면, Engine의 AI 문맥·근거 검증은 함수 ID·디컴파일 차이에 결합돼 있다. 파일/엔터티/manifest 근거 ID와 전용 결과 표시를 함께 확장한다.

권장 자료형은 `native_functions`, `managed_members`, `package_inventory`, `javascript_modules`, `wasm_module`, `android_package`처럼 관측한 내용을 구분하는 것이다. 모든 종류는 입력 SHA·도구/버전·계약·실행 위치·근거·부분 범위·상한을 공통으로 기록한다. 의미가 다른 점수를 하나의 종합 정확도로 합치지 않는다.

### 첫 ZIP 기능의 구체적 최소 범위

- 지원: 유효한 ZIP 두 개의 구성원 목록·경로·항목 종류·실제 스트리밍 내용 SHA·크기를 읽고 추가/삭제/변경을 표시.
- 기본은 추출·대상 실행 없음. 중첩 압축은 자동 재귀하지 않고 명시적 선택/깊이 한도. 구성원 내용은 출력 한도·암호화·unsupported 상태를 보존.
- 작업 시간·항목 수·선언 및 실제 확장 바이트·압축비·메모리/출력 상한. 경로 traversal/절대/drive/UNC, 중복 이름, 대소문자 충돌, 링크, 손상·CRC·암호화를 명시적으로 처리.
- 독립 oracle: 손으로 쓴 고정 경로·바이트 정답. 목록 순서/압축률/타임스탬프만 다른 패키지는 내용 동일, 연산자 또는 리소스 바이트가 바뀐 패키지는 해당 구성원 변경. 빈 파일과 미관측을 구분.
- 회귀: 정상·변경·추가/삭제·빈 ZIP/빈 파일·중복·case collision·암호화·손상·과도한 확장·취소/timeout·입력변경·재시작 보관·보고서 escape·근거 ID 재검증.
- 결과 표시는 **패키지 구성 차이**다. 프로그램 동작 일치율은 미측정. 다음 단계에서 사용자가 선택한 구성원만 기존 ELF/PE/.NET 구조 분석으로 넘기고 `archive_sha → member_path → member_sha → child_run` 연결을 보존.

MSIX/AppX는 이 inventory 위에 manifest·리소스·아키텍처·패키지 서명 정보의 관측을 추가할 후보다. 서명이 존재함과 발급자/신뢰 검증 성공은 별도다. IPA/DMG는 같은 확장자 목록에 넣었다고 지원되지 않으며 컨테이너 형식·파서·플랫폼 전제를 별도 확인한다.

## 조사한 공식 근거와 적용 판단

- Python `zipfile`은 ZIP 목록·읽기를 제공하며 손상/암호화·확장과 자원 문제를 별도로 다룬다. 위의 한도·경로 정책은 이 도구의 존재만으로 해결되지 않으므로 Recheck 계약에서 구현해야 한다. [Python 공식 문서](https://docs.python.org/3/library/zipfile.html#decompression-pitfalls)
- Electron의 `@electron/asar`는 ASAR 목록·구성원 읽기/추출을 제공한다. 이를 구성 비교의 입력으로 쓰는 것은 설계 제안이며, Electron 앱의 실제 동작 관측을 대신하지 않는다. [Electron 공식 ASAR 저장소](https://github.com/electron/asar)
- Android `apkanalyzer`는 APK 파일·manifest·DEX·리소스 정보를 읽고 APK 크기 차이를 비교하는 명령을 제공한다. 권한/SDK/클래스 관측을 Recheck에 연결할 후보다. [Android 공식 문서](https://developer.android.com/tools/apkanalyzer)
- JADX는 APK/DEX 등에서 추정 Java와 리소스를 얻는 도구이며 모든 코드를 완전히 디컴파일하지 못할 수 있음을 명시한다. 누락을 정상 빈 메서드로 처리하지 않는다. [JADX 공식 저장소](https://github.com/skylot/jadx)
- WABT는 wasm2wat·wasm-objdump·wasm-validate 등 구조 확인 도구를 제공한다. 별도의 실행 도구가 있다고 해서 호스트 실행을 허용하는 것은 아니다. [WABT 공식 저장소](https://github.com/WebAssembly/wabt)
- Microsoft는 MSIX/AppX의 단일 아키텍처 패키지와 여러 아키텍처의 bundle을 구분한다. 패키지 단위와 앱 실행의 지원 범위를 나누는 설계가 필요하다. [Microsoft 공식 문서](https://learn.microsoft.com/en-us/windows/msix/package/packaging-uwp-apps)

외부 도구는 이번 조사에서 새로 설치하거나 실행하지 않았다. 버전은 실제 구현 시 고정·해시·고지/재배포 조건을 검토하고, 도구의 지원 설명을 Recheck 실측 지원으로 표시하지 않는다. 기능 구현은 재현 실패 검사→최소 구현→회귀/전체 검사→source identity→새 staging→실제 EXE/전체 ZIP→정확한 SHA CI/새 릴리스 순서로 진행한다.
