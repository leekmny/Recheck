## 팀에서 사용하는 방법

1. 새 PC나 팀원은 [기여 안내](../../CONTRIBUTING.md)와 [GitHub 개발 절차](../GITHUB_WORKFLOW.md)를 읽고 자기 개발 환경을 준비합니다.
2. 인증·저장·배포·주요 의존성처럼 이후 작업에 영향을 주는 선택은 [템플릿](adr-template.md)을 복사해 다음 번호의 ADR로 작성합니다. 작은 오타 수정이나 단순한 국소 수정마다 ADR을 만들 필요는 없습니다.
3. PR에는 관련 ADR을 연결하고, 최종 구현과 검증 결과를 적습니다. 검토한 대안이 있다면 채택하지 않은 이유와 다시 검토할 조건을 남깁니다.
4. 결정이 바뀌면 기존 기록을 지우지 않고 새 ADR을 연결해 대체 관계를 표시합니다. 상태 변경과 확인된 사실은 날짜와 함께 갱신합니다.

상태는 `제안`, `수락`, `기각`, `보류`, `폐기`, `다른 ADR로 대체` 등을 사용합니다. 실험 승인에는 적용 범위를 함께 적습니다. 실험을 허용했다는 사실만으로 제품 기능이나 배포 변경이 승인된 것으로 해석하지 않습니다.

작업 기록에는 **완료한 일·앞으로 할 일·하지 않은 일과 이유**를 구분합니다. [작업 기록 양식](work-log-template.md)을 복사하고 [실제 실험 기록](../../experiments/embedded_login/README.md)을 참고하세요. ADR은 선택의 근거를 보존하고, 작업 기록은 구현 진행과 실제 관찰을 남깁니다. 두 문서를 같은 내용으로 채울 필요는 없습니다. 계정 식별정보·키·토큰·쿠키·인증 URL 전체·개인 분석 자료·개인 PC 경로는 공개 기록에 넣지 않습니다.
